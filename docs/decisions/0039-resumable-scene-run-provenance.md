# ADR 0039 — Resumable scene-run provenance and budgets

Engineering decision record for the remaining operational/provenance slice in Track D/P5 of the
September audit. This change records execution evidence; it does not claim that the compiler authored
prose or that any literary/reader experiment succeeded.

## 1. Failure observed

Execution evidence was fragmented. Role-runner attempts preserve review-provider usage, while
selection experiments have their own operation ledger. Generation and revision work outside a
selection experiment had no general scene-level manifest, no declared run budget, and no durable
resume state. A process interruption therefore left humans/agents to infer which planned operations
had completed, and a later matched-cost study could not point to one experiment-wide execution spine.

## 2. Root layer

This is an **operational provenance** problem. It belongs below literary evaluation and above the
individual provider adapters. The compiler must bind and preserve evidence without claiming ownership
of external/manual generation.

## 3. Decision

Each operational scene run lives under `.runs/scene-runs/<scene>/<run>/` and has:

- one immutable `manifest.json` declaring ordered step ids/phases and optional operation/token/cost
  budgets;
- create-only operation artifacts, including failures and retries;
- optional caller idempotency keys so retrying a record after a crash returns the same evidence;
- content-addressed frozen candidate snapshots for every candidate-affecting operation; and
- derived status rather than a mutable progress file.

Status recomputes completed/failed/pending steps from operation artifacts, verifies frozen candidate
and linked source hashes, and reports when current candidate bytes have changed since an operation.
Editing the working candidate therefore makes the binding stale without destroying the reviewed or
generated bytes that the operation actually used.

Multiple successful records for one declared step are preserved and counted when they represent work
that actually happened. Callers that need crash/retry deduplication supply an idempotency key; reusing
that key with different evidence is refused.

## 4. Accounting and budgets

Operations may carry provider/model/request/model-version/finish metadata, input/output/total tokens,
cost and latency. Executor kind distinguishes compiler/human work from model-backed or unknown work.
For external-model, role-runner, and unknown executors, absent token or cost evidence stays explicitly
unknown. A zero is counted only when zero was actually recorded.

If input, output, and total token counts are all supplied, total must equal the two components. Token
counts, monetary values, latency, budgets, and preflight estimates reject negative, boolean, and
non-finite values.

Budgets may bound operation count, total tokens, and USD cost. `scene_run_budget` / `scene_run.py
budget` preflight one additional operation. Reaching an exact token/cost limit is allowed for the
operation being preflighted; once recorded usage is at that limit, the next operation is blocked.
Exact call-count exhaustion likewise blocks the next operation;
missing prior usage or a missing estimate makes token/cost projection `unknown`. Recording an action
that already happened is never refused because it exceeded budget: preserving the overrun/failure is
more important than hiding it. The next preflight exposes the breach.

## 5. Role-runner integration

`link_scene_run_review` imports an existing `.runs/reviews/...` role-runner attempt. It never repeats
the provider call. The scene-run operation preserves the review artifact hash, packet hash, role,
validation status, provider/model/request metadata, latency, and known token usage. Dollar cost remains
unknown unless a caller supplies a defensible value.

Role packets intentionally rename candidate prose to `submission.md`. The linker therefore binds the
packet's SHA-256 to the unique matching working candidate, or accepts an explicit candidate filename
when current hashes are ambiguous. If the exact bytes cannot be recovered from the current candidate
or an already frozen run snapshot, linkage is refused rather than guessed.

## 6. Public workflow

`scripts/scene_run.py` and the MCP tools expose start/resume, status, budget preflight, generic
operation recording, and role-review linkage. Generation/revision remain external/manual unless an
explicit adapter exists; callers record their real provenance after producing candidate bytes.

This gives a single process/run identity across generation, critique, revision, selection, reader and
promotion phases without turning the deterministic compiler into a prose generator.

## 7. Regression evidence

`tests/test_run_manifest.py` covers idempotent start/resume, preserved failed attempts, idempotent
operation retries, frozen candidate bytes plus stale detection, unknown usage semantics, budget
preflight including exact/zero limits, malformed accounting rejection, duplicate real attempts,
path/hash confinement, invalid-manifest handling, lossless role-runner import, and MCP schema parity.

## 8. Limits

- This infrastructure cannot recover provider usage a caller never supplies and an adapter never
  observed.
- It does not make historical selection experiments retroactively complete; those retain their own
  frozen ledgers.
- A matched-cost claim still requires a study to route every relevant call through this ledger (or
  bind equivalent evidence) and then run the predeclared human/model evaluation.
- Budget accounting is descriptive unless a caller actually performs the preflight before the next
  external operation.

## 9. Approval

Authorized as implementation of the user-requested September audit/plan. It changes evidence
infrastructure only and grants no new promotion, critic, or process-change authority.
